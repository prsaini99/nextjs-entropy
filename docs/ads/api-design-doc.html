1. Executive summary

StackBinary is a software and AI engineering company based in India. We advertise our own services on Google Ads through a single account that we own and operate ourselves. We do not manage Google Ads campaigns on behalf of any other company.

We are building an internal tool that lets our marketing team analyse and manage our own Google Ads account. It performs three functions:

  • Reporting — retrieving search term, campaign, ad group, keyword, asset and audience statistics via GAQL, and joining them with the Google Analytics 4 measurement we already collect from our website.
  • Keyword research — generating keyword ideas and budget forecasts to plan which queries to bid on.
  • Campaign creation and management — creating and adjusting our own campaigns, ad groups, ads, keywords and negative keywords.

The defining characteristic of this tool is that no change reaches Google Ads without explicit human authorisation. Every write operation produces a preview and returns it for review; a separate, deliberate confirmation call is required to apply it. Dry-run mode is the default, and the tool cannot make a live change until an operator explicitly disables it for that specific action. Section 6 describes these controls in detail.

Access is limited to StackBinary employees. The tool is not offered to third parties, not resold, has no external users, and exposes no public interface.

2. Business model and motivation

StackBinary earns revenue from professional services: custom software development, cloud engineering, and AI implementation for our clients. We do not sell advertising technology, do not resell Google Ads data, and do not operate an advertising product.

We advertise our own services to generate inbound enquiries. Our website captures leads through a contact form which records Google Analytics 4 events and the gclid click identifier at the point of submission.

Two specific gaps motivate this work.

Attribution. Google Analytics 4 tells us which sessions converted; it does not tell us which search query the user typed. That lives only in the Google Ads search terms report. Today a team member exports it to CSV by hand and reconciles it against GA4 manually — slow, error prone, and done rarely enough that budget decisions rest on stale data.

Iteration speed. Acting on what we learn currently means retyping negative keywords and bid adjustments through the web interface one at a time. Being able to compose a change, review it as a single reviewable plan, and apply it once approved makes the loop from observation to action materially shorter and less error prone than manual entry.

4. System architecture

The integration is built on AdLoop (github.com/kLOsk/adloop, MIT licence), an open-source Google Ads MCP server, pinned to a specific reviewed commit and self-hosted. It runs as a local process on an employee workstation. The Google Ads API version is pinned to v24 so that API changes cannot silently alter behaviour.

Our marketing and engineering team interacts with it through an AI assistant licensed to StackBinary and used under our own company account. The assistant composes reporting questions and proposed changes; it cannot apply a change on its own, because applying requires the separate confirmation step described in section 6. Retrieved data is used solely for our own internal analysis and is not sold, published or shared with third parties.

5. Google Ads API usage

5.1 Read operations

Sixteen read tools, all issuing GAQL through GoogleAdsService.SearchStream or Search:

list_accounts, get_campaign_performance, get_ad_performance, get_keyword_performance, get_search_terms, get_negative_keywords, get_negative_keyword_lists, get_negative_keyword_list_keywords, get_negative_keyword_list_campaigns, get_recommendations, get_pmax_performance, get_asset_performance, get_detailed_asset_performance, get_audience_performance, get_demographic_targeting, run_gaql

Representative query — search terms, the primary reporting need:

SELECT
  search_term_view.search_term,
  campaign.name,
  ad_group.name,
  metrics.impressions,
  metrics.clicks,
  metrics.cost_micros,
  metrics.conversions
FROM search_term_view
WHERE segments.date DURING LAST_30_DAYS
ORDER BY metrics.cost_micros DESC

6. Safety controls and change authorisation

This section is the core of our design. Because the tool can modify a live advertising account, we treat every path to a mutation as something that must be deliberately opened rather than accidentally taken.

6.1 Two-step write model

A write tool never writes. Calling draft_campaign or add_negative_keywords produces a change plan — a structured, human-readable description of what would change — and returns it. Nothing has been sent to Google Ads at this point. Applying that plan requires a separate confirm_and_apply call carrying the plan's identifier.

The practical consequence: an operator always sees the full, concrete effect of a change before anything is committed, and the act of approving is distinct from the act of composing.

6.2 Dry-run by default

The configuration key require_dry_run defaults to true. Additionally, confirm_and_apply itself defaults to dry_run=true — so even the confirmation step simulates by default, and applying a real change requires explicitly passing dry_run=false. A freshly installed instance cannot alter our Google Ads account at all until a human changes configuration and then explicitly opts out of dry-run for a specific action.

6.3 Spend and configuration guardrails

  • Daily budget cap — max_daily_budget (default 50.00) bounds any budget the tool may set, independent of what is requested.
  • Bid increase caps — limit how far a bid may be raised in one operation.
  • Unsafe combinations blocked — Broad Match paired with Manual CPC is rejected outright, as it is a common cause of runaway spend.
  • New entities launch paused — newly created campaigns and ads are created in a paused state, so nothing begins spending without a further deliberate action.
  • Audit log — every plan and every applied change is recorded locally.

6.4 Scope limits

The OAuth user is a StackBinary employee whose Google Ads access covers only account 659-437-9515. No other account is reachable, and no account belonging to any client or third party is in scope.

7. Representative workflows

Workflow A — reporting. An operator asks which search terms consumed budget without converting. The tool runs the search_term_view query in 5.1 and returns rows. No write path is involved.

Workflow B — acting on that report. The operator decides several terms are irrelevant and asks for them to be excluded. add_negative_keywords builds a plan listing exactly which negatives would be added to which campaign, and returns it. The operator reads the plan. If correct, they call confirm_and_apply with the plan identifier and explicitly leave dry-run mode. Only then does a SharedSetService / AdGroupCriterionService mutation occur.

Workflow C — planning new coverage. discover_keywords returns keyword ideas and volumes; estimate_budget forecasts cost. Both are read-only research. If the operator then wants a campaign, draft_campaign produces a plan — created paused, and bounded by the configured budget cap — which again requires explicit confirmation to apply.

8. Data handling and security

  • Developer token — stored in a local environment file on the workstation, excluded from version control. Never transmitted to any third party.
  • OAuth credentials — desktop-type OAuth 2.0 client issued from our own Google Cloud project (668883874314), consent screen configured as Internal to our Workspace domain. The client secret file is stored locally and excluded from version control.
  • Retrieved data — held in memory for the duration of a query and rendered for internal review. No warehouse and no long-term store of Google Ads data.
  • Onward transfer — none. Report data is not sold, published, syndicated, or used to deliver any service to any other company.
  • Third-party code — AdLoop is open source, self-hosted, MIT licensed, and pinned to a reviewed commit. No vendor operates it, no vendor holds our token, and no data passes through any vendor's infrastructure. We do not use the hosted commercial variant.
  • API version — pinned to v24 so that upstream changes cannot silently alter behaviour.
